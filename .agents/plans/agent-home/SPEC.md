# Agent home — file definitions with one operational history

## Outcome

All implementation entry points resolve the same role, task-kind workflow, grouped ownership and canonical task definition under `.agents`. Every task has a separate folder and shared implementation template. Guidance is concise, skills are referenced once, and verification matches the effect/risk of the change. Existing canonical task IDs and reported work survive migration.

## Definition selection

The sole source selector is `authority.yaml`. Full per-step files own normalized kind/effect/owner/read/write/needs/acceptance/verification after activation. The catalog owns hierarchy and references without copying task bodies. Roles own execution responsibilities; grouped ownership segments own exact scopes/public seams/dependencies and local domain skills. Workflows own supported kinds and procedures. Operational SQLite owns reports, sessions, claims, facts and evidence.

The shared writer selects legacy input only during an explicit migration. Archives preserve original source/data; old aggregate files become forwarding descriptors. Retired control paths reserve historical task scopes, and those historical tasks are visibly blocked from reviving a second runtime. New work uses a refined current scope.

## Evidence policy

Review is sufficient for low-risk prose/metadata when an attributed assessment checks links, scope and meaning. Smoke checks suit a small reversible operational change. Behavior or contract changes use focused valid/failure/state-transition checks. Migration, concurrency and shared resources require integration/recovery proof. A kind label does not grant writes or mandate a full suite. Existing required checks remain binding until the supported evidence-contract change is delivered; never use `true` or a fabricated pass to make a prose step green.

## Migration and rollback

Capture online SQLite backup and matching source/configuration before conversion. Rehearse on a disposable copy including all current task/report hashes. Stage file definitions without selecting them; compare source generations and consumer outputs; activate through one revision-checked writer only after restore and critical-consumer parity are demonstrated. AR-17 stages trusted dual-source/dual-path observation before AR-13 can activate. Keep legacy sources as read-only provenance/derived compatibility while consumers still need them. Physical runtime movement follows definition activation as its own recoverable step. Source release data is never copied.

Low-risk documentation assets need structural review, not an invented application suite. Source migration checks are owned by relevant source/verification tasks. Build, browser retention and provider-account acceptance apply only to affected behavior and authorized promotion. A passing typecheck or template presence is not implementation completion.
