# Whiteboard roadmap

Canonical task definitions are generated by the shared planner in `../steps/`; this file is navigation and sequencing, not a second status source. The associated [specification](SPEC.md) settles the intended initial contracts and acceptance.

1. [WB-OWNERS](../steps/WB-OWNERS/step.yaml), [WB-CONTRACTS](../steps/WB-CONTRACTS/step.yaml) and [WB-DOC](../steps/WB-DOC/step.yaml): declare consumer dependencies, then settle public DTOs, owner methods, composition hooks and validated documents.
2. [WB-STATE](../steps/WB-STATE/step.yaml) and [WB-VIEW](../steps/WB-VIEW/step.yaml): retained persistence owner and interactive view. These may run concurrently after contracts/model are settled, using disjoint exact files. One parent checks their combined behavior.
3. [WB-PACKAGE](../steps/WB-PACKAGE/step.yaml), [WB-SHELL](../steps/WB-SHELL/step.yaml), [WB-COMPOSE](../steps/WB-COMPOSE/step.yaml) and [WB-RUNTIME](../steps/WB-RUNTIME/step.yaml): dependency delivery, workspace controls, root composition and runtime retention. Sequence shared files; display unavailable states until each optional seam is connected.
4. [WB-VERIFY](../steps/WB-VERIFY/step.yaml): disposable keyboard/persistence/HMR and cleanup evidence. Require actual results before implementation completion.

[AGENTS-VIEW-SPEC](../steps/AGENTS-VIEW-SPEC/step.yaml) records active-agent visibility and owner-scoped parallel orchestration alongside this feature. It must reconcile current Harness/Process work rather than create a competing execution authority.

Plan population and ownership metadata can be complete while every product implementation task remains pending. Historical Obsidian/HMR source observations do not count as Whiteboard runtime evidence.
