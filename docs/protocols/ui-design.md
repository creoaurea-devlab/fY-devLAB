# Prototyping — design and engineering workflow

These are actionable review instructions, not a running designer/agent service. Source, canonical ownership and real behavior evidence remain authoritative. Use this guide from the preview's source menu and pass it as `--rules docs/protocols/ui-design.md` for UI tasks.

1. **Confirm the design question and target.** Read the selected project's AGENTS.md, active WISDOHM BOOT/rules/maintenance, canonical source ownership, this guide and the exact source/style files. Confirm project identity, attached API origin and current source hashes before editing. Never substitute the original DevTest/Full checkout for this independent edition.
2. **Use the named prototyping skill.** Read `docs/skills/prototype/SKILL.md`, then UI.md for layout exploration or LOGIC.md for a state-model question. The actual question determines the branch. Temporary `prototype-*` code remains adjacent to its owning UI. Apply the user's compact existing-menu preference; no extra large headers or bars.
3. **Keep a clear experiment.** Compare up to three structurally different designs. Kanban begins with A=current columns, B=dense execution table, C=ownership swimlanes. Use the existing preview View menu and shareable variant URLs. Show current variant/simulated state concisely. Prototype UI is development-only; real planning data is read-only. Local simulated state is disposable and never becomes project progress or a Wisdom receipt.
4. **Design within the app.** Evaluate the element inside the real editor/preview with existing typography, color/spacing tokens and compact controls. Bar heights are a baseline, not a reason to retain redundant rows. Prefer one contextual header per surface, collapsible sections and existing menus/drawers. Keep terminal identity/status visible; merge repeated global and pane actions without losing multi-pane selection, resize, ownership settings or keyboard access. Collapsing presentation must retain mounted resource owners. Use source-inspected existing elements before adding controls; avoid ornamental dashboards, excessive padding, duplicate toolbars and color-only variants.
5. **Cover actual interaction states.** Inspect normal, empty, loading, error, stale, disabled and long-content cases. Check fit/desktop/mobile and1440/820 layouts; keep usable reading and pointer areas without horizontal overflow. A visible control must work, be deliberately disabled with a reason, or be absent.
6. **Preserve accessibility.** Prefer native controls, visible focus, meaningful labels and appropriate landmarks. Maintain keyboard order and Escape/focus return. Do not steal arrow keys from input, textarea, select, contenteditable, terminal or other composite controls. Distinguish focus/selection and never use color alone for status. See W3C's [keyboard guidance](https://www.w3.org/WAI/ARIA/apg/practices/keyboard-interface/).
7. **Make scoped engineering changes.** Keep behavior in its owning module, neutral contracts at public seams, explicit acyclic dependencies and one authority per fact. UI/style edits must preserve canonical planning validation/persistence and workspace/terminal owners. Stop and redeclare scope for service/kernel/policy behavior changes. Prototype data and layout experiments never authorize backend replacements or invented capabilities.
8. **Use live preview truthfully.** Save source through expected-hash guards. Vite/React compatible UI updates should refresh the isolated element while the outer app's drafts/preview/terminal identities remain. The source inspector shows annotations and accessible style-token evidence, not guaranteed full CSS provenance. HMR connection is observed cooperatively; changed owner/bootstrap/server implementations require explicit controlled reload/restart. [Pinned React plugin4.7.0](https://github.com/vitejs/vite-plugin-react/blob/plugin-react%404.7.0/packages/plugin-react/README.md) defines this development facility.
9. **Test the reusable host, observe the throwaway design.** Run relevant types, contracts, source/ownership and interaction/HMR/retention checks on disposable fixtures. Do not add test frameworks or abstractions just for throwaway variants. Keep before/after screenshots and actual observations, not invented performance or compliance scores. A skill profile and a copied brief do not launch an agent; provider execution remains separate.
10. **Record a decision before promotion.** Ask the user to choose or combine a variant. Record which question was settled and why. Then integrate a reviewed implementation into the actual UI through normal scope/tests and archive/remove losing experiments. No automatic apply-to-production control is provided. User requested no Git: capture a verified source archive and decision note instead of creating a branch/commit.
11. **Update WISDOHM honestly.** Record actual changelog/progress and affected codebase/registry/decision notes after coherent changes; use current review and verification. Unknown host usage is not a measurement and must never become a fabricated gated DONE. The documented administrative waiver is explicit; keep normal guards intact. Product planning JSON remains separate from operational SQLite.

12. **Retain state across compatible refresh.** Resource effects must clean up correctly. Scope-reset effects must compare actual project/state identity before clearing UI state: React Fast Refresh can rerun effects even when their dependency values stay unchanged. Verify this with a real compatible TSX edit and retained search/drafts, rather than assuming the iframe staying mounted is sufficient.
