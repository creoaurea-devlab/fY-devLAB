## Existing task contract versus Continuity

`packages/contracts/src/planning.ts:4–42` accepts only `begin/verify/finish/reset/move`, strict fields, UUID command ID, expected revision and SHA-256 digest. `:49–83` projects segment → milestone → slice → task, execution statuses pending/running/review/complete, dependencies, declared checks/write paths and service-derived actions. Installed Kanban polls only while visible, invalidates generations on project changes, ignores wrong-project results and serializes commands (`MilestoneBoard.tsx:101–176,178–208`). Preserve these protections and dispose timers/listeners.

Prototype `tobeimplemented/CA_devLAB_Kanban_v2_Continuity/contracts.ts:5–55,56–153` instead models capabilities, exact rule versions, blueprints, work cards, releases and journal events. A capability is not a milestone; a release is not a task's complete status; a work-card ticket checkbox is not successful host verification. Existing strict planning schemas cannot transport these records by silently adding properties. Prototype `contracts.ts:155–180` is a proposed boundary only. README `:48–76` explicitly says releases use manual references/review, no CI/database/Cordis/agent launch is connected, localStorage is not concurrent durable authority. Its demonstration statuses and evidence must never seed verified DevTest progress.

Minimum contract decision: retain the existing Planning transport/client seam and introduce a versioned Continuity namespace/read projection and command schemas through public contracts. Let one Planning owner validate and dispatch both existing execution intents and Continuity metadata intents; keep pure domain validation/projection in that plugin until there is a demonstrated second consumer. A separate graph database, generic event-sourcing platform, domain-framework package and six new plugins are unnecessary initially.
