## Confirmed user behavior
- A normal dock-header click shows one terminal. Shift-click adds/removes individual terminals in the same dock panel. Dock splits are horizontal: side-by-side terminals with draggable vertical separators. No arbitrary UI selection cap; respect actual service limits and show capacity errors.
- A separate Terminal workspace view can expand inside the application, preserve surrounding navigation, resize its height, arrange terminals side-by-side or top/bottom, and reorder them. Canvas and dock/workspace show the same sessions without restarting them.
- Rename terminals. Assign an existing canonical ownership. Provide Off, Guided and Strict modes; displayed mode and effective server-enforced mode must agree.
- Fork means a fresh terminal with inherited ownership and mode. Threads/conversation branches are explicitly removed from scope. Do not clone a live process or imply that provider conversation state was copied.

## Contracts and owners
Use existing capability plugins, not shell/kernel business logic. Before parallel implementation, one integration writer establishes additive `CanvasViewOptions.dockedTerminals?: readonly {nodeId:string; sessionId:string}[]`, retains singular compatibility and updates Canvas resize suppression for every presented session. ui-shell owns selected/ordered pane identity and layout; ui-terminal owns xterm observers; TerminalService owns processes; transport stays SSE/POST. One writer owns shared contracts, packaging, lockfiles, provenance, registry coverage and shared memory. Separate workers may then own shell UI and backend implementation scopes.
Server-issued session policy must bind project, canonical ownership ID, effective mode and policy revision; callers cannot submit arbitrary allowlists or downgrade a running session. Exact schema is a T02 output after the Strict probe. Changing effective confinement requires explicit new-session/restart semantics; never relabel a running process as newly restricted.
Retain mounted pane identities in the existing terminal panel. Dedicated mode repositions/expands that panel, avoiding a second set of live TerminalViews. Normal click replaces visible selection; Shift-click toggles membership. Rename updates existing node label. Fork adds a fresh UUID/node with inherited settings and parentNodeId; it never replays old commands automatically.

## Strict mode feasibility gate
A starting directory, label, prompt, `cd` wrapper or tmux session is not a filesystem restriction. Registry owners often share directories and own exact files. A writable parent-directory mount would expose siblings; exact-file mounts can reject atomic rename saves. A viable design must test symlinks, hardlinks, child processes, new files, sockets and host-side write services, plus provider connectivity. Read-only host mounts alone do not isolate Unix socket/API access. Do not call Strict enforced while those escape paths remain open.
T01 must choose and document an enforceable boundary, private scratch, network/credential policy and supported edit operations. If the available host cannot provide it, Strict is visibly unavailable and launching Strict fails closed. Guided is advisory, never a quiet Strict fallback. User requests an on/off-style control; Off/Guided/Strict can be represented with clearly named states and lock indicator.

## Performance and recovery gates
Provisional acceptance workload: Linux Node24.18, current Chromium at1440x900 and820x900; eight PTYs, four visible, each producing32KiB/s plus a10MiB burst in one session. Capture machine/versions, baseline and repeated p50/p95 browser-event-to-visible-terminal-frame proxy latency; target p95<=100ms while typing/Ctrl-C. Divider input-to-layout target p95<=50ms. These are proposed budgets, not measured outcomes or physical input-to-photon measurements. Profile memory and prove bounded growth/recovery rather than claiming unlimited terminals. Retune only against recorded baseline and the user's actual target workload.
Reconnect/replay, hidden panes, GPU fallback, full-screen TUIs and duplicated observers need real tests. Backend restart/tmux and reboot recovery are separate checks. No runtime state changes or process restarts on the user's instance until an isolated candidate passes and active sessions/drafts are accounted for.
